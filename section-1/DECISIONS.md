# Decision Log — Section 1

## D1: จะเก็บสถานะผู้ใช้ที่ Login ไว้ที่ไหน
- ทางเลือกที่คิดไว้: (A) React Context (B) Redux (C) ส่งข้อมูลผู้ใช้ผ่าน props ระหว่างหน้า
- เลือก: A — React Context
- เพราะ: ข้อมูลที่แชร์มีขอบเขตเล็ก คือผู้ใช้ปัจจุบันและการ Login/Logout และทั้ง route guard กับหน้าตาม role ต้องอ่านข้อมูลชุดเดียวกัน จึงใช้ Context ได้โดยไม่เพิ่ม dependency
- ข้อเสียของ A ที่ยอมรับ: เมื่อ state โตขึ้นหรือมีการเปลี่ยนถี่ component ที่อ่าน Context อาจ render ซ้ำมากขึ้น และ Context ไม่ได้ให้เครื่องมือจัดการ async state แบบครบชุด

## D2: จะจำลองการ Login และการเรียก API อย่างไร
- ทางเลือกที่คิดไว้: (A) ตรวจบัญชีแบบ synchronous ในหน้า Login (B) ทำฟังก์ชัน mock API ที่คืน Promise และหน่วงเวลาด้วย setTimeout (C) ตั้ง backend จริง
- เลือก: B — mock API แบบ asynchronous
- เพราะ: โจทย์กำหนดให้การตรวจสอบผ่านฟังก์ชันจำลอง API และ UI ต้องแสดงสถานะกำลังโหลด วิธีนี้ทำให้ทดลอง loading และ error ได้จริงโดยไม่ต้องมี backend
- ข้อเสียของ B ที่ยอมรับ: ข้อมูลอยู่ในหน่วยความจำและหายเมื่อ reload จึงไม่เหมาะกับการใช้งานจริงหรือการทดสอบความคงทนของข้อมูล

## D3: จะจัดเก็บความสัมพันธ์ระหว่างผู้ใช้ โครงการ และงานอย่างไร
- ทางเลือกที่คิดไว้: (A) รวมข้อมูลทั้งหมดไว้ในตารางเดียว (B) แยก users, projects และ tasks พร้อม foreign key (C) เก็บผู้รับผิดชอบเป็นข้อความใน task
- เลือก: B — แยกตารางและใช้ foreign key
- เพราะ: งานผูกกับโครงการและผู้รับผิดชอบที่เป็นผู้ใช้ คีย์อ้างอิงช่วยรักษาความถูกต้องของความสัมพันธ์ และทำให้ query งานตามผู้รับผิดชอบหรือโครงการได้ชัดเจน
- ข้อเสียของ B ที่ยอมรับ: การอ่านข้อมูลที่ต้องการชื่อผู้ใช้หรือชื่อโครงการต้องใช้ JOIN และการเปลี่ยน schema ต้องจัดการ migration

## D4: จะป้องกันไม่ให้ผู้ใช้เข้า route ของ role อื่นอย่างไร
- ทางเลือกที่คิดไว้: (A) ซ่อนลิงก์ในเมนูอย่างเดียว (B) ตรวจ role ใน route guard และ redirect พร้อมข้อความแจ้ง (C) แสดงหน้าเดิมแล้วซ่อนเนื้อหาบางส่วน
- เลือก: B — ตรวจสิทธิ์ที่ route guard
- เพราะ: การซ่อนลิงก์ไม่ป้องกันการพิมพ์ URL โดยตรง ส่วน guard ทำให้การเข้า route ที่ไม่ตรง role มีผลลัพธ์ชัดเจนตามโจทย์ และแยกจากการแสดงเมนู
- ข้อเสียของ B ที่ยอมรับ: route guard ฝั่ง client เป็นเพียงการควบคุมการนำทาง ไม่ใช่ขอบเขตความปลอดภัยสำหรับระบบจริง เพราะผู้ใช้ควบคุม client ได้; backend ต้องตรวจสิทธิ์ซ้ำ

## D5: Employee จะเปลี่ยนสถานะ Task อย่างไร
- ทางเลือกที่คิดไว้: (A) ให้เลือกสถานะใดก็ได้ (B) แสดงปุ่ม Done เฉพาะงาน To Do และไม่ให้ย้อนจาก Done (C) ปิดการเปลี่ยนสถานะทั้งหมดหลังงานถูกมอบหมาย
- เลือก: B — ให้เปลี่ยนได้เฉพาะ To Do → Done
- เพราะ: ตรงกับกฎสิทธิ์ของ Employee โดยตรง และ UI สามารถป้องกันการกระทำที่ไม่อนุญาตได้อย่างเข้าใจง่าย
- ข้อเสียของ B ที่ยอมรับ: เมื่อทำ Done แล้ว Employee แก้สถานะไม่ได้ แม้กดผิด; ระบบจริงควรให้ Admin เป็นผู้แก้ไขตามสิทธิ์ที่กำหนด

## การใช้ AI

ผู้ทำงานควรตรวจและปรับเนื้อหาให้สอดคล้องกับการออกแบบและอธิบายเหตุผลของแต่ละข้อได้
